# T04 — Wire HolderGate into the RugCheck stage (F1, part 4 of 4)

## Goal
When `holder_gate_enabled` is on (and `holder_distribution_enabled` is on), the RugCheck holder rule runs on
**ordinary holders only**. A holder counts as a pool account when its `address` OR its `owner` is one of the
token's known pool accounts: the pool ids, the reserve/vault accounts, and the `KNOWN_AMM_AUTHORITIES`.
The rule then rejects on top-1 / top-3 / top-10, and on missing holder data.
Pool accounts come from the bot's own pool decoders via `crate::pools::token_pools(chain, mint)`.
With the gate off, the behaviour is byte-for-byte upstream, and `token_pools` is never called.

The classifier already does the address-OR-owner match (`src/fork/holder_gate.rs`, `PoolContext::is_pool_holder`,
committed in T03). **Do not change `src/fork/`.** There is no chain-side change.

## Exact changes in `src/filtering/sources/rugcheck.rs`
Imports: add `use crate::fork::holder_gate::{self, PoolContext};`.

1. `RugcheckStage::evaluate`: rename `_chain` to `chain` and call `evaluate_stage(chain, token, config)`.
2. `evaluate_stage(chain: ChainId, token, config)`: same body, except the last line becomes:
   ```rust
   // FORK: holder gate (F1). Pool accounts come from the bot's own pool decoders; the lookup
   // runs only with the gate on, so the gate-off path stays exactly upstream.
   let pools = if config.rugcheck.holder_gate_enabled && config.rugcheck.holder_distribution_enabled {
       PoolContext::from_pools(&crate::pools::token_pools(chain, &token.mint))
   } else {

   };

   ```
3. Rename the current body of `pub fn evaluate(token, config)` into a new
   `pub fn evaluate_with_pools(token: &Token, config: &RugCheckFilters, pools: &PoolContext) -> Result<(), FilterRejectionReason>`.
   Keep `pub fn evaluate(token, config)` with the same signature and doc. Its body is
   `evaluate_with_pools(token, config, &PoolContext::with_known_authorities())`, with a `// FORK:` comment saying it
   does no pool lookup. Inside, the only change is `check_holder_distribution(token, config, pools)`.
4. `check_holder_distribution(token, config, pools: &PoolContext)`: keep the `holder_distribution_enabled` early
   return and the whole `min_unique_holders` block exactly as they are. Directly after that block, before
   `three_largest_pcts`, insert:
   ```rust

   if config.holder_gate_enabled {
       return check_ordinary_holders(token, config, pools);
   }
   ```
   Everything below (the upstream top-1/top-3 code) stays untouched.
5. New private fn, placed after `check_holder_distribution`:
   ```rust
   // FORK: holder gate (F1). Top-1/3/10 on ordinary holders only. An empty list, or a list with no ordinary
   // holder left (all pool accounts or non-finite pct), is missing data and rejects. An account the classifier
   // cannot place is kept and counted, which errs toward rejecting.
   fn check_ordinary_holders(token: &Token, config: &RugCheckFilters, pools: &PoolContext) -> Option<FilterRejectionReason> {
       if token.top_holders.is_empty() {
           return Some(FilterRejectionReason::RugcheckTopHoldersMissing);
       }
       let ordinary = holder_gate::ordinary_holders(&token.top_holders, pools);
       let (Some(top1), Some(top3), Some(top10)) = (
           holder_gate::top_n_sum(&ordinary, 1),
           holder_gate::top_n_sum(&ordinary, 3),
           holder_gate::top_n_sum(&ordinary, 10),
       ) else {
           return Some(FilterRejectionReason::RugcheckTopHoldersMissing);
       };
       if exceeds(top1, config.max_top_holder_pct) {
           return Some(FilterRejectionReason::RugcheckTopHolderTooHigh);
       }
       if exceeds(top3, config.max_top_3_holders_pct) {
           return Some(FilterRejectionReason::RugcheckTop3HoldersTooHigh);
       }
       if exceeds(top10, config.max_top_10_holders_pct) {
           return Some(FilterRejectionReason::RugcheckTop10HoldersTooHigh);
       }
       None
   }

   /// FORK: strict `>`, the same as upstream (a value equal to the limit passes). A NaN limit rejects.
   fn exceeds(sum: f64, limit: f64) -> bool {
       limit.is_nan() || sum > limit
   }
   ```
No `unwrap()`/`expect()` in production code. No other production change.

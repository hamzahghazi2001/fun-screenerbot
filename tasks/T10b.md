# T10b — Close the third-slot race: re-check the slot cap after the permit (F3 follow-up) · claude

## Problem (from T10)
With `dynamic_size_enabled = true` the global position semaphore holds
`max(max_open_positions, third_slot_max_positions)` = 3 permits, while the cap check
(`safety::check_position_limits`) allows 2 below $40. The cap check and the permit are not atomic:
with 1 position open, two entries can both pass the check (used 1 < 2), both get a permit
(semaphore 3), and 3 positions open below $40.

## Fix
Right after `acquire_global_position_permit()` in `open_position_*`, count the permits in use,
including this one and every other in-flight open, and refuse if that count exceeds the live slot cap.
```
in_use = semaphore_capacity_at_init - semaphore.available_permits()   // read after our acquire
allowed iff  !dynamic_size_enabled  ||  in_use <= get_max_open_positions()
refused  →   return Err(positions::Error::SlotUnavailable { remaining: 0 })
```
The early return drops the not-yet-forgotten permit, so the slot goes back (open.rs:115-117 contract).
`SlotUnavailable` is already the typed "no slot" outcome: retryable (error.rs:234), Info severity,
and reported as a slot refusal, not an execution failure (trader/types.rs:111).

Why this closes it: each opener reads `available_permits()` after its own `try_acquire`, so of two
racing openers at least the second sees both permits taken (in_use 3 > 2) and backs off. If both
read after both acquired, both back off. That is a false refusal, it is safe, and the next entry
cycle retries. It can never allow too many: a permit taken by any opener is counted by every
later read.

## Runtime semaphore mutations (owner question 1, answered during implementation)
Permit total is `available + held`. Paths after init:
- startup only, in `start_positions_manager_service` before the trader service (which depends on
  "positions") can open: `reconcile_global_position_semaphore` (worker.rs:257: leak release
  state.rs add_permits, consume via try_acquire+forget) and `rebuild_position_slot_holders` (worker.rs:261).
- runtime: `open.rs` forget (free → held), `reclaim_position_slot` try_acquire+forget (free → held),
  `release_position_slot` add_permits(1) once per registered holder (held → free). These keep the total.
- runtime drift: rebuild registers EVERY capacity-consuming open position as a holder, while reconcile
  consumes at most `capacity` permits. With more positions open at boot than the semaphore holds, each
  extra holder's close adds a permit it never took, so the total grows. Accounted for by recording
  `STARTUP_SLOT_OVERFLOW = holders - consumed` in `rebuild_position_slot_holders`, and
  `in_use = capacity + overflow_at_boot - available`.

## Behaviour
- Off (`dynamic_size_enabled = false`): the check is skipped (`permit_within_cap` is always true), so
  the behaviour is upstream's. Upstream's own race after lowering `max_open_positions` live is left as is.
- On, ≥ $40: cap 3 = semaphore 3, so the check never refuses beyond what the semaphore does.
- On, < $40 or price/balance unknown: cap 2; a third concurrent open is refused and its permit released.
- Leaked permits (a double release) make `in_use` undercount. That is the existing invariant
  `a_slot_is_released_at_most_once_however_many_paths_run` guards, so T10b does not cover it.
- Not touched: `reclaim_position_slot` / `try_consume_global_position_permit` (an unarchived
  position re-entering management, not a new open). It can still take the third permit below $40;
  noted for the review.
